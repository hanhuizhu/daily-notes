# 审查标准

## 审查目标

0. **卡控问题** (checkpoint-error)
  - 禁止 if 条件中出现赋值操作（仅指 `=` 赋值），比较运算（`===` / `!==` / `==` / `!=`）不属于该规则
  - 全局环境变量判断必须使用 ===，且不能直接判断线上环境变量，eg：production、prod 等
  - 变量名、类型、实际用途必须一致，禁止语义错用（如 `total` 当 `count`、`isEnabled` 赋非布尔语义值）
  - 禁止提交 dead code（未使用的变量/函数/导入、不可达分支、长期注释掉的保留逻辑）
  - 禁止硬编码（密钥/令牌、环境地址、业务关键常量需统一走配置或常量定义）
  - 禁止使用 continue
  - 禁止使用多重嵌套的三元表达式
  - 业务运行路径禁止 mock 后端接口数据
  - 异步提交按钮必须防重复触发（loading 禁用、节流或幂等保护至少一项）

1. **运行时错误** (runtime-error)
   - 可能为 `null` / `undefined` 的值在使用前必须判空（属性访问、解构、调用）
   - 类型使用必须与声明一致，禁止通过 `any` / 强制断言绕过类型检查
   - 数组、字符串下标访问前必须保证索引在有效范围内
   - `Promise` 必须被 `await`/`return` 或显式处理拒绝（`try/catch` 或 `.catch`）
   - 事件监听器、定时器、订阅、连接等资源必须在生命周期结束时释放
   - 异步请求必须处理竞态（取消旧请求或仅接受最后一次响应），禁止旧响应覆盖新状态

2. **安全漏洞** (security)
   - 用户输入写入 HTML/URL/脚本上下文前必须转义或白名单过滤
   - 禁止直接使用 `v-html` / `dangerouslySetInnerHTML` 渲染不可信输入
   - 代码、日志、响应体中禁止明文输出密钥/令牌/密码/身份证号等敏感信息

3. **性能问题** (performance)
   - 非必要禁止超过两层循环嵌套（可用索引/映射替代时必须替代）
   - 长生命周期对象禁止持续增长且无清理（缓存、集合、队列）
   - 循环中禁止频繁 DOM 读写，必须批量更新或合并重排
   - 数据查询必须有明确过滤条件与分页，禁止无条件全量读取
   - 主线程禁止长时间同步计算（单次任务 > 16ms 需拆分或异步化）
   - 长列表（>200 项）必须使用分页、虚拟滚动或分段渲染
   - 高开销计算必须缓存（memo/computed），禁止每次渲染重复计算

4. **逻辑错误** (logic-error)
   - 边界输入必须覆盖（空值、0、负数、最大值、单元素）
   - 条件分支必须互斥且完整，禁止出现永真/永假判断
   - 列表渲染 `key` 必须稳定且唯一，禁止在可变列表中使用索引 `index` 作为 `key`
   - 注释、命名、文案说明与实际实现必须一致；若注释声明了业务规则、前置条件、兜底策略或副作用，代码行为必须与之匹配
   - 变更必须符合当前代码上下文与既有业务链路，禁止局部修改后破坏上下游约束、状态流转、字段语义或调用时序
   - 本次变更若只修改了业务链路的一部分，但未同步更新相关状态枚举、字段映射、校验规则、常量、文案、埋点或调用方适配，按逻辑错误处理
   - 注释掉的代码若会改变现有业务逻辑、分支行为、返回值、状态更新或异常处理，按逻辑错误处理，不能视为普通注释问题
   - 禁止错误注释误导业务判断，包括过期注释、反向描述、与真实开关条件/生效范围不一致的说明
   - 结合上下文识别业务逻辑异常：如金额/数量/状态字段混用，成功失败态处理反转，前置校验缺失，兜底值覆盖真实状态，关键业务分支遗漏或执行顺序错误
   - 条件取反、布尔开关语义、状态枚举映射、权限判断、早返回条件若发生语义反转，且与上下文预期不一致，按逻辑错误处理

## Diff 审查补充标准

当基于 code diff 进行审查时，必须额外遵循以下判定规则，避免误报和臆断：

1. **新问题必须有正向证据**
   - 仅当问题出现在 `+` 新增行，或可由本次变更后的保留上下文明确证明时，才可输出为本次新问题。
2. **删除行不得作为新问题依据**
   - 仅存在于 `-` 删除行的旧问题，不得作为本次新增问题输出；删除有问题的旧代码默认视为风险下降。
3. **注释类问题仅限影响逻辑的场景**
   - 纯说明性、风格性注释不审查；只有当注释会影响业务规则理解、条件判断、开关范围、副作用认知或注释掉的代码会改变逻辑时，才可输出问题。
4. **业务逻辑问题必须结合可见上下文判断**
   - 必须基于同 hunk、同文件可见上下文或本次变更中可确认的调用链证据判断；不得仅凭命名猜测、经验猜测或缺失上下文的常识推断输出 mustFix。
5. **证据不足默认不阻断**
   - 若当前 diff 无法提供足够证据证明问题成立，默认不输出；尤其禁止将“可能有问题”的猜测上升为 mustFix。

## 风险分级与阻断规则

| 级别 | 含义 | 是否阻断提交 |
|------|------|------------|
| **mustFix** | 卡控问题、致命问题，会导致运行时错误、安全漏洞或严重性能问题，必须修复 | ✅ 阻断 |
| **shouldFix** | 潜在问题或不良实践，建议修复但不强制 | ❌ 不阻断 |

**各问题类型对应级别：**
1. 🔴 卡控问题 (checkpoint-error) — mustFix，阻断提交
2. 🔴 运行时错误 (runtime-error) — mustFix，阻断提交
3. 🔴 安全漏洞 (security) — mustFix，阻断提交
4. 🔴 逻辑错误 (logic-error) — mustFix，阻断提交
5. 🟡 性能问题 (performance) — shouldFix，不阻断

## 历史问题修复验证补充标准

当进入“历史问题修复验证”模式时，必须额外遵循以下判定规则，避免误报“未修复”：

1. **删除优先视为修复**
   - 历史问题对应代码若仅出现在 diff 的 `-` 删除行，且未在 `+` 新增行或变更后保留代码中继续出现，判定为已修复。
2. **文件删除视为问题已移除**
   - 若历史问题所在文件被整体删除（如 `deleted file mode`、`+++ /dev/null`），该文件中的历史问题默认判定为已修复。
3. **不存在即修复**
   - 若历史报告中的问题代码在当前变更证据中已不存在，不得继续判定为未修复。
4. **未修复必须有正向证据**
   - 只有在当前有效代码中可明确定位到同类问题（例如存在于 `+` 新增行或变更后仍保留的相关代码）时，才可判定为未修复。
5. **证据不足默认不阻断**
   - 对“是否仍存在”证据不足时，不得输出为未修复，避免阻断提交。
