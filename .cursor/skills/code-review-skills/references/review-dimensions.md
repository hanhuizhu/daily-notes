# 审查维度说明

每次 review 都固定分成以下四个部分。四个部分职责独立，避免同一条问题在多个部分重复出现。

## 1. 业务功能的实现

- 只审“这次改动有没有把需求或实施计划里的功能做完整”
- 关注漏实现、错实现、范围漂移、用户流程不完整、上下游链路缺口

## 2. 代码的质量

- 只审“实现方式本身有没有违反明确的代码质量规则”
- 严格复用 [code-quality-rules.md](code-quality-rules.md)
- 没有规则依据的问题，不放在这一部分

## 3. 架构的合理性

- 只审“实现是否落在正确的层次和模块边界上”
- 如果有实施计划，以计划中的模块拆分、职责边界、调用关系、文件落点为准
- 如果没有实施计划，只在当前 diff 可证明的范围内判断是否存在明显的职责混乱或错误分层

## 4. 项目 rules 的遵循情况

- 只审“改动是否违反了仓库已有的编码规则”
- 优先通过 [project-rules-index.md](project-rules-index.md) 找到相关 rules
- 尽量指明具体规则文件，而不是笼统地说“违反项目规范”

## 去重原则

- 需求不一致，放“业务功能的实现”
- 明确违反质量规则，放“代码的质量”
- 分层或职责不合理，放“架构的合理性”
- 明确违反 `.cursor/rules/`，放“项目 rules 的遵循情况”

如果一条问题同时命中多个部分，优先放在“最接近根因”的那个部分，其他部分不要重复报。
