# 审查评分规则

评分只做轻量风险量化，不替代文字结论。

## 目标

- 让每次 review 都有一致的定级和打分口径
- 优先体现实际影响和是否必须修复
- 简单、可解释，不做复杂模型

## 使用顺序

1. 先判断问题是否属于当前 diff 且证据充分；不成立时不要为了凑等级输出 finding
2. 再按“实际后果、影响范围、可恢复性、替代路径”确定 `severity`
3. 再独立判断问题是否必须在合入前修复，确定 `mustFix`
4. 最后根据 `severity + mustFix` 查表扣分

不要先看扣分多少再反推问题等级，也不要用 `mustFix` 代替严重程度。

## 不构成 finding 的情况

以下内容不进入 S1-S4，也不参与评分：

- 不在本次需求、验收范围或明确支持范围内的能力
- 仅存在于未改动历史代码，且本次改动没有依赖、扩大或恶化的问题
- 缺少当前 diff、需求、规则或可复现路径支撑的猜测；需要确认时放入 `questions`
- 明确约定为非评分提醒的内容，例如 `meta.codeQualityRiskTips`

## 问题定级逻辑

按下列四项判断，命中多个等级时取后果最严重的等级，不做平均：

- **实际后果**：是否造成越权、隐私泄露、资金或数据错误、核心流程不可用、普通功能退化
- **影响范围**：影响全部用户、部分角色、单个功能，还是只影响代码维护
- **可恢复性**：是否不可逆，是否需要人工修数，是否可重试恢复
- **替代路径**：用户是否存在可靠且成本可接受的绕过方式

发生概率只用于校准影响范围：触发条件明确且极窄时可以降一级；但已确认的越权、敏感数据泄露、不可逆资金或数据损坏不得仅因“概率低”降级。

### 判定优先级

按以下顺序判断，前面的明确证据优先于后面的降级因素：

1. 已确认的安全、权限、隐私、合规、不可逆资金或数据后果，直接按 S1 判断
2. 明确验收点在正常用户路径稳定失败，至少按 S2 判断；即使用户可以重新操作，也不能仅凭替代路径降为 S3
3. 重复订单、重复结算等关键数据一致性问题默认按 S2；只有存在不可逆资金后果、无法修复或持续扩散证据时才升为 S1
4. 仅在非核心能力、边界条件或低频路径中触发，并且存在可靠替代路径时，才按 S3 判断
5. 不改变业务结果的问题才按 S4 判断

“核心验收点”必须有需求、验收标准或既有主流程证据；如果需求已把某行为列为明确验收点，正常路径稳定违反该行为时，无需 reviewer 再主观判断它是否足够核心。

## 问题定级矩阵

| 等级 | 定义 | 典型判定条件 | `mustFix` 默认值 | 对应扣分（`true` / `false`） |
|---|---|---|---|---:|
| `S1` 阻断 | 已确认会造成不可接受后果，或核心业务整体不可用 | 越权访问、敏感信息泄露、不可逆资金/数据损坏；核心提交链路对全部或大范围用户必定不可用；违反明确合规红线 | `true` | `40 / 25` |
| `S2` 高 | 核心功能错误或重要数据存在可恢复的一致性风险 | 核心验收点漏实现/错实现；部分角色无法完成主流程；重复订单、重复结算、错误状态流转但可修复；稳定回归会误导业务判断 | `true` | `25 / 15` |
| `S3` 中 | 局部功能退化，影响受限且存在可靠替代路径 | 非核心流程异常；特定条件下的功能错误；重复请求但未触及关键数据；明确规则违例会增加回归或维护风险 | `false` | `12 / 6` |
| `S4` 低 | 不影响当前业务结果的轻微规范或维护性问题 | 命名、局部一致性、低影响可读性问题；轻微交互瑕疵；不改变运行结果的普通规则违例 | `false` | `4 / 2` |

定级补充：

- 安全、权限、隐私、合规问题优先按已确认的后果定级，不因影响用户数量少自动降为 S3/S4
- 数据或资金问题需区分是否可恢复：不可逆或可能持续扩散通常为 S1，可修复且范围受控通常为 S2
- “核心功能”的判断必须引用需求、验收点或现有主流程证据，不能只凭 reviewer 主观判断
- 可靠替代路径只用于区分边界/非核心问题，不能覆盖明确验收点在正常路径上的稳定失败
- 测试缺失本身通常不高于 S3；只有当前 diff 已有明确缺陷证据时，才按缺陷后果升为 S1/S2

## `mustFix` 判定

`severity` 表示影响大小，`mustFix` 表示是否允许带着问题合入，两者必须分别判断。

满足任一条件时，设为 `mustFix: true`：

- 已确认的安全、权限、隐私、合规、资金或数据完整性问题
- 核心验收点未实现、实现错误，或构建/运行失败导致需求无法交付
- 问题会在正常用户路径稳定触发，且没有可靠替代路径
- 明确规则标注为强制执行、不可违反或会被 CI/发布门禁阻断

只有同时满足以下条件时，才可设为 `mustFix: false`：

- 不涉及安全、权限、隐私、合规、资金或不可逆数据风险
- 不阻断核心验收点，且存在可靠的绕过或恢复方式
- 延后修复不会扩大影响，当前合入风险可被明确说明

组合校准：

- `S1` 原则上必须是 `mustFix: true`；只有存在明确、可追溯的风险接受结论时才允许为 `false`，reviewer 不得自行豁免
- `S2` 默认 `mustFix: true`；满足全部非阻断条件时可以为 `false`
- `S3` 默认 `mustFix: false`；命中强制规则或交付门禁时可以为 `true`
- `S4` 默认 `mustFix: false`；纯风格偏好不得设为 `true`，明确强制规则违例可以设为 `true`

## 起始分

- 总分默认 `100`

## 扣分规则

按单条 finding 扣分：

| 严重程度 | `mustFix: true` | `mustFix: false` |
|---|---:|---:|
| `S1` | 40 | 25 |
| `S2` | 25 | 15 |
| `S3` | 12 | 6 |
| `S4` | 4 | 2 |

补充规则：
- 同一根因不要重复扣分；如果同类问题在多个文件重复出现，可以合并成一条 finding
- `questions` 不直接扣分，但如果待确认问题影响核心业务判断，结论应偏保守
- 每条 finding 必须先完成定级矩阵和 `mustFix` 校准，再进入扣分；不得为了达到预期分数调整等级
- 分数最低为 `0`

## 风险等级

根据最终得分输出风险等级：

| 分数区间 | 风险等级 | 建议 |
|---|---|---|
| `90-100` | 低风险 | 可合入，关注验证缺口 |
| `75-89` | 中风险 | 建议修复后合入 |
| `50-74` | 高风险 | 不建议直接合入 |
| `0-49` | 严重风险 | 必须修复后再审 |

## Ready 结论建议

- 存在任意 `S1` 且 `mustFix: true`：`Ready: No`
- 存在 `S2` 且 `mustFix: true`，或总分低于 `75`：`Ready: With fixes`
- 无 must-fix 问题，且总分不低于 `90`：`Ready: Yes`
- 其他情况：结合问题集中度与验证缺口，在 `With fixes` 和 `Yes` 间判断

## HTML 报告中的展示项

HTML 报告至少展示：
- 总分
- 风险等级
- must-fix 问题数量
- 各严重程度问题数量
- `Ready` 结论

## 实施建议

- 评分只消费结构化 findings，不要从 markdown 文本二次解析
- 输出报告时同时展示“为什么是这个分数”，避免黑盒感
