# Requirements To Superpower

需求开发工作流。

把需求类任务统一编排为：

- 需求收集
- 需求澄清，或跳过
- 实施计划，或跳过
- 开发执行
- 完成前验证

## 硬规则

1. 流程推进由 agent 按本 skill 自行判断并直接执行，不向用户建议下一步，也不让用户在流程阶段或执行方式之间做选择。
2. 进入任一阶段前，必须先完成该阶段播报；不允许未播报就直接进入下一阶段，也不向用户暴露内部跳转判断。
3. 如果给了 Flash 地址，先完成需求事实收集；用户指令优先，且只有在需求不存在任何疑问、歧义或待澄清点时，才允许跳过需求澄清。只要需求表述非常泛化、范围不收敛或缺少关键业务语义，就必须进入需求澄清，不允许自行猜测。
4. 实施计划在获得人工确认前，不允许进入开发执行或完成前验证。
5. 开发执行完成后，必须立即进入完成前验证。

## 阶段播报规则

进入阶段前必须先做醒目的单独播报，建议单独成段，不和其他内容混在同一行。

### 播报格式

统一使用下面这种清晰格式：

```md
### 当前阶段：阶段名称
```

例如：

- `### 当前阶段：需求收集`
- `### 当前阶段：需求澄清`
- `### 当前阶段：实施计划`
- `### 当前阶段：开发执行`
- `### 当前阶段：完成前验证`

### 播报要求

- 阶段播报必须先于该阶段的任何分析、提问、计划或执行内容出现
- 阶段播报尽量单独成段，避免埋在普通句子里
- 阶段切换时必须重新播报，不能沿用上一个阶段的标题
- 禁止“先进入下一阶段，后补阶段播报”

## 流程

```text
用户请求
  ↓
需求收集
  ├─ Flash 地址 → mcp-flash.get_story_task_description
  └─ 纯文本需求 → 直接整理
  ↓
先判断是否仍有疑问、歧义、方案点或待澄清项
  ├─ 有 → 进入需求澄清（人工确认）
  └─ 无 → 继续判断是否仍需拆任务、排顺序、补 guardrails
       ├─ 需要 → 进入实施计划（人工确认）
       └─ 不需要 → 直接进入开发执行
  ↓
开发执行
  ↓
完成前验证
```

## 需求收集

这是本 skill 的新增前置阶段，用来统一收集输入并决定后续走向。

所有命中本 skill 的请求，都必须先进入本阶段。本阶段是唯一入口；在本阶段完成前，不允许进入 `需求澄清`、`实施计划`、`开发执行` 或 `完成前验证`。

### 输入处理

**Flash 地址：**

1. 解析 `storyId`
2. 调用 `mcp-flash.get_story_task_description`
3. 只基于返回结果提炼事实
4. 若失败或地址不完整，说明阻塞点，再退回“用户描述 + 代码上下文”模式

**直接需求描述：**

1. 直接整理需求
2. 结合代码库定位相关页面、模块、接口、组件、状态管理和相似实现
3. 只有在需求不存在任何疑问、歧义或待澄清点时，才可以跳过 `需求澄清`

### 需求收集输出

至少整理出：

- 需求目标
- 业务背景
- 变更范围
- 涉及模块 / 页面 / 接口
- 已知约束
- 验收标准
- 风险 / 未决问题

本阶段的目标是先把事实收集完整，再决定后续进入 `需求澄清`、`实施计划` 还是 `开发执行`；不允许在事实尚未整理完成时，直接开始写计划或进入执行。

## 跳转判断

以下规则仅用于 agent 根据现有条件自行判断下一步应触发哪个阶段，不需要把跳转判断过程展示给用户，也不需要让用户在这些阶段之间做选择；只需在判断完成后播报当前进入的阶段。

判断顺序固定如下，不允许跳步：

1. 先完成 `需求收集`
2. 先判断是否还存在任何疑问、歧义、方案点或待澄清项
3. 只有在完全不需要澄清时，才允许判断是否进入 `实施计划`
4. 只有在不需要澄清、也不需要再拆任务和补 guardrails 时，才允许直接进入 `开发执行`

### 进入需求澄清

满足任一项就进入：

- 需求目标不明确
- 需求表述非常泛化
- 业务规则不明确
- 变更范围不明确
- 验收标准缺失或模糊
- 存在任何待确认的方案点
- 存在任何待确认的字段、交互、排序、筛选、导出、接口口径或边界条件
- 有多条合理改造路径但用户未表达偏好
- 需要先做方案比较才能决定实现
- 代码库里存在多种参考实现，取舍会影响设计
- 范围不收敛或缺少关键业务语义，继续推进会依赖猜测

一句话判断：

- **不知道“该做成什么样”时，进入需求澄清。**

只有在需求目标、业务规则、变更范围、验收标准都已明确，且不存在任何疑问、歧义或待澄清点时，才允许跳过本阶段。凡是继续推进需要 agent 自行补全、脑补或猜测的情况，都必须进入本阶段。

本阶段解决的是“做法是否已经定下来”。只要做法、口径或关键方案点还没定，就必须先进入本阶段，不允许带着待确认方案点进入 `实施计划`。

### 进入实施计划

满足以下条件时进入：

- 已知道做成什么样
- 不再需要方案比较
- 但仍需拆任务、排顺序、补测试和实现 guardrails
- 任务不是一次小改动，而是多步骤、多文件或多人协作开发

一句话判断：

- **知道“做什么”，但还需要拆成“怎么分步做”时，进入实施计划。**

本阶段只处理“方案已定后的任务拆解与落地计划”。如果仍然存在待确认方案点，就不能进入本阶段，必须先回到 `需求澄清`。

### 直接执行

仅当以下条件同时满足时允许：

- 用户给出的需求已经非常明确
- 用户已经给出了具体执行步骤，或至少给出了明确修改建议
- 改动范围集中，风险可控
- 不需要再做方案比较
- 不需要再拆出多阶段计划才能安全执行
- 验收口径足够明确

一句话判断：

- **“改什么、怎么改、改到什么算完成”都已清楚时，可直接进入开发执行。**

### 不允许直接执行

出现任一项就不能直接执行：

- 关键业务歧义仍在
- 验收标准不足
- 改动跨多个子系统且边界不清
- 实现路线还未定
- 还需要先确认模板、组件库方案或页面结构

## 需求澄清

进入本阶段后：

0. 使用 superpower 的 `brainstorming` skill
1. 基于需求收集结果，先逐项澄清所有疑问、歧义、待确认方案点和待澄清问题
2. 只有在澄清完成后，如仍存在多种合理实现路径，再给出 2-3 个可行方案与取舍
3. 在方案比较基础上明确推荐方案
4. 形成设计结论 / spec 草案
5. 等待人工确认

本阶段的顺序是：先把问题问清楚，再比较方案；可行方案与取舍用于帮助确定做法，不用于替代问题澄清本身。

禁止：

- 方案未确认就进入 `实施计划`
- 仍有任何疑问、歧义、待确认方案点或未决问题时结束本阶段
- 用“先给几个方案”代替对关键问题的逐项澄清
- spec 未稳定就开始编码

## 实施计划

在本阶段，除了写任务，还必须把公司规则写进 plan。

本阶段使用 superpower 的 `writing-plans` skill。

plan 中至少显式包含：

- 页面类型：列表页 / 表单页 / 通用新页面
- 参考模板：
  - `templates/scene-list.md`
  - `templates/scene-form.md`
  - `templates/common-page.md`
- 规则文件：
  - `.cursor/rules/001-ai-friendly-standard.mdc`
- 如果 plan 涉及 `@tuhu/shop-mars-pc` 的组件库组件，可以调用 `mcp-mars-pc` 的 `listMrpComponents` 工具查看有哪些可用组件，并将组件选型写入 plan
- 需要复用的页面、组件、hooks、services、表格组织方式
- 组件拆分边界
- 页面目录结构要求
- 接口返回值处理约束
- 特殊代码模版或项目内推荐写法

如果人工评审或后续澄清导致 plan 发生变化，必须先回写并更新 plan，再继续推进。

plan 产出后必须等待人工确认。

在人工确认前，禁止：

- 触发开发执行的任何下游 skill
- 播报 `当前阶段：开发执行`
- 播报 `当前阶段：完成前验证`
- 进入完成前验证

## 开发执行

本阶段根据任务特点，选择使用 superpower 的 `subagent-driven-development` 或 `executing-plans` skill进行执行。

如果实施过程中使用了 `@tuhu/shop-mars-pc` 的组件库组件，可以调用 `mcp-mars-pc` 的 `listMrpComponents` 工具查看有哪些可用组件，并使用 `getMrpComponentsDetail` 工具查询具体组件用法后再落地实现。

### 执行方式选择

优先选择 superpower 的 `subagent-driven-development`，用于：

- 计划中任务可拆成多个相对独立的小任务
- 有并行价值
- 每个任务边界清晰
- 需要 reviewer 子代理多轮把关

优先选择 superpower 的 `executing-plans`，用于：

- 任务强耦合
- plan 较短
- 变更集中在少量核心文件
- 更适合在当前线程顺序执行

开发执行完成后，不能直接结束，必须立即进入完成前验证。

## 完成前验证

本阶段使用 superpower 的 `verification-before-completion` skill。

代码修改完成后必须进入本阶段。

本阶段是强制阶段，不能省略，不能把“已完成开发”视为任务结束。

至少验证：

- 需求里的核心验收点
- 相关测试 / 构建 / lint / 类型检查
- 若是 bugfix，验证原始问题已消失
- 若是需求开发，回看需求收集阶段整理的验收标准

## 输出边界

- 本 skill 只负责阶段播报、需求收集、阶段跳转判断和触发下游 superpower skill。
- 一旦触发下游 skill，后续输出与执行都以下游 skill 原始定义为准；本 skill 不再额外改写其模板与流程。
